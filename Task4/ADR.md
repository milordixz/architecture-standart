## **Нефункциональные требования**

| №    | Требование                                                                                                                                                                                       |
|------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| RN01 | Публичный read API ≥99,9%/24×7; p95≤300 мс на согласованной нагрузке. Цели наследуют R-01/R-02/P-01; предварительно 300 операторов, до 50 чтений/с, уточнить M1.                                 |
| RN02 | После публикации в АБС ставка видна в кол-центре банка ≤60 с, импортирована партнёром ≤15 мин в штатном режиме. Дополнительные целевые значения; включают все этапы, не только выгрузку файла.   |
| RN03 | Файлы передаются шифрованным каналом, без персональных данных; у партнёра доступ только к собственным export/ack каталогам.                                                                      |
| RN04 | At-least-once обработка, проверка хеша/подписи и монотонной версии, атомарная активация; повреждённый/старый файл не заменяет действующий.                                                       |
| RN05 | Работа сервиса не добавляет поток чтений в Oracle; снимки хранятся отдельно. Используются Java Spring Boot, MS SQL и Kafka как в ADR-001.                                                        |
| RN06 | Один экземпляр export job обрабатывается по lease, хранится состояние и попытки. После сбоя обработчик продолжает, а не создаёт неконтролируемый поток файлов.                                   |
| RN07 | Все копии имеют validUntil и время обновления; просроченные ставки блокируются в UI, API и партнёрском импортёре. Максимальный срок снимка предлагается 24 часа, даже если ставка не изменилась. |
| RN08 | Мониторинг возраста версии, export backlog, ошибок импорта, времени без ACK; audit по exportId. Отсутствие ACK за 15 мин — инцидент интеграции.                                                  |

## **Решение**

### Контекст и границы

Маркетинговая кампания увеличит звонки. Операторам обоих кол-центров нужны актуальные публичные ставки. Система
банковского кол-центра расширяема, партнёр принимает файлы. Личные предложения, кредитные риски, заявки и персональные
данные партнёру не передаются.

Источник ставок — **согласованный каталог АБС из ADR-001**. На MVP бизнес может продолжать расчёты в Excel, но файл
загружается и проверяется в АБС, а дальше распространяется только опубликованная версия.

### Допущения, которые необходимо проверить

**B01:** фразу условия «Нет возможности сделать API-вызовы (например, через SFTP-протокол)» трактуем так: SFTP допустим
как файловый транспорт, но API бизнес-системы партнёра отсутствует. Банк размещает файлы в SFTP DMZ, партнёр забирает их
и кладёт ACK-файл. До M2 нужно согласовать транспорт и ACK; при запрете SFTP используется другой защищённый файловый
канал.

**B02:** партнёр может доработать импорт, ACK и отображение срока актуальности. **B03:** сроки доставки, TTL и формат
согласуются банком и партнёром; это проектные цели, а не факты условия.

L3 раскрывает **один контейнер «Сервис распространения ставок»**: consumer, query API, экспортёр, файловый transport,
ACK worker. Это компоненты одного Java Spring Boot приложения, а не самостоятельные микросервисы. MS SQL, Kafka, DMZ
SFTP и обе системы кол-центров показаны как соседние контейнеры/системы. Прочие потоки депозитной заявки не дублируются.

| Компонент                      | Ответственность                                                                                                                                |
|--------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------|
| Public rates consumer          | Читает только публичные события Kafka, фильтрует неподходящую схему/версию; одна транзакция inbox + snapshot + export job                      |
| Query API                      | Отдаёт активный снимок с version/validUntil банковскому кол-центру; сервисная авторизация; запрет просроченного каталога                       |
| Snapshot exporter              | Делает полный снимок, manifest и подпись; создаёт стабильный exportId; формирует новый экспорт при событии и регулярное продление актуальности |
| File transport worker          | Загружает комплект в DMZ SFTP, публикует manifest последним; retries/backoff и состояние передачи                                              |
| ACK worker / reconciliation    | Читает подтверждения партнёра, сверяет ID/версию, фиксирует APPLIED/REJECTED; контролирует timeout и replay                                    |
| Хранилище (соседний контейнер) | Отдельная MS SQL БД: snapshots, inbox, exports, acknowledgements, leases; не таблицы каталога АБС                                              |

### Контракт файлов и свежесть

- Кодировка UTF-8, разделитель `;`, даты ISO 8601 UTC, десятичный разделитель `.`; деньги и ставки передаются точными
  decimal-строками. Схема версии 1 согласуется с партнёром; escaping CSV обязателен.
- `rates_<version>_<exportId>.csv`: productId, productType, currency, termMin/termMax, amountMin/amountMax, rate,
  conditions, validFrom, validUntil. Для отозванных продуктов применяется новый полный снимок без них; пустой снимок
  явно означает отсутствие действующих предложений.
- `manifest_<exportId>.json`: schemaVersion, exportId, catalogueVersion, generatedAt, validFrom, validUntil, rowCount,
  fileName, sha256, signature/keyId. Подпись банка проверяется импортёром; ключи заранее обменены по независимому
  каналу.
- Каталог не содержит clientId, персональных ставок, телефонов, Ф. И. О. или данных кредитного риска. Все поля — из
  allowlist; права Kafka исключают чтение personal-топиков.
- Manifest выгружается последним через rename из `.tmp`; партнёр обрабатывает только финальные manifest. Он сверяет
  хеш/подпись, порядок версий, полную загрузку, не скачивает по произвольным внешним URL из manifest.
- Импорт атомарно переключает указатель активной версии. Повтор exportId возвращает тот же ACK. Старшая версия не
  заменяется младшей, а одна версия с другим хешем считается ошибкой.
- `ack_<exportId>.json`: partnerId, exportId, catalogueVersion, status=APPLIED/REJECTED, appliedAt, errorCode. Файл
  подтверждается учётной записью/подписью партнёра; права не допускают подмену его другим клиентом шлюза.
- Предлагаемый polling партнёром/ACK worker — каждые 5 мин; файл создаётся сразу после обновления. Запас в 15 мин
  покрывает импорт/подтверждение. Интервалы — B03.
- Срок снимка не продлевается лишь потому, что экспортёр работает: продление допускается только при подтверждённой
  актуальности источника АБС (версионированный heartbeat/переутверждение). При отсутствии подтверждения источник
  считается устаревшим. Для покрытия задержки доставки плановые изменения публикуются заранее с validFrom; экстренный
  отзыв распространяется немедленно, но краткое окно рассогласования неизбежно.

### Размещение и отказоустойчивость

Сервис имеет экземпляры в двух ЦОД, использует SQL AG по той же модели, что ADR-001. Lease экспортёра хранится
транзакционно; failover не оставляет двух активных job на один exportId. Kafka/public outbox переигрываются после DR;
ACK/inbox дедуплицируют повторы.

SFTP — отдельный управляемый файловый шлюз в DMZ, реплицируемое хранилище и резервный узел/адрес. Партнёр инициирует
соединение извне по allowlist, не получает доступ к внутренним БД/брокеру. Доступ к каталогу настроен отдельно от
отправки файлов. Дубли после переключения безопасны благодаря версии и exportId.

Нет ACK или партнёр недоступен: штатный банковский кол-центр продолжает читать API. Партнёр использует последнюю *
*непросроченную** версию с видимым временем обновления. По истечении срока точная ставка не обещается, клиент
переадресуется в банк. Система не может гарантировать физическую доставку при длительной недоступности внешнего
партнёра; RN02 измеряется, нарушения явно видны.

### Приёмка

1. Изменение ставки в АБС появляется в обоих кол-центрах в пределах RN02; номера версий совпадают.
2. Повтор, повреждённый файл и доставка старой версии не меняют каталог неверно; есть ACK/ошибка.
3. Остановка партнёра, SFTP или consumer: retry и alert работают; после validUntil отображение ставки запрещено.
4. Отзыв ставки и пустой снимок обрабатываются корректно; персональные поля отсутствуют.
5. Потеря ЦОД/worker после передачи, но до записи статуса не приводит к бесконечному повтору или двум активным версиям.

## **Альтернативы**

| Альтернатива                                  | Причина отказа / применимость                                                                                                                                         |
|-----------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Письма с Excel напрямую двум кол-центрам      | Быстро, но не обеспечивает версию, срок действия, подтверждение импорта и контроль доступа. Только аварийный согласованный ручной канал, не штатная архитектура       |
| HTTP API для обоих кол-центров                | Для банка выбран; партнёр не может его предоставить/использовать по ограничению кейса                                                                                 |
| Прямой SQL-доступ к АБС                       | Перегрузка и раскрытие внутренней БД; нарушает +I-01 и +SEC-02                                                                                                        |
| Подключить партнёра к Kafka                   | Новая технологическая зависимость, открытие внутреннего брокера и несоответствие файловому контракту                                                                  |
| Включить экспорт в основной депозитный сервис | Меньше deployment-единиц, но внешняя файловая интеграция и её сбои становятся частью финансового сервиса; выбран отдельный контейнер с узким публичным набором данных |

## **Недостатки, ограничения, риски**

| Риск                                 | Последствие и реакция                                                                                                                  |
|--------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------|
| B01/B02 не подтверждены              | Согласовать канал/контракт до M2. Без импорта с контролем версии нельзя объявлять партнёрский сценарий готовым; PM пересматривает план |
| Файловая задержка и экстренный отзыв | Не мгновенная консистентность; timestamp/validUntil, ранняя публикация, финальные условия всегда проверяет АБС при открытии            |
| Ручной Excel-расчёт ошибочен         | Автоматизация передачи не исправляет бизнес-ошибку; проверка/согласование версии в АБС и аудит автора                                  |
| Новая система распространения        | Дополнительные дежурство, SQL/DMZ, секреты и тесты восстановления; владелец IT-интеграций                                              |
| Партнёр игнорирует TTL               | Некорректные консультации; контракт, тесты UI/import, сверка ACK и контрольные звонки до запуска                                       |
