`OpenDepositRequested` содержит eventId, applicationId, clientId, productId, accountId, amount, currency, rateVersion,
consentId и timestamp. В Kafka не передаются OTP или полные документы. Для лидов передаются только необходимые Ф. И. О.,
телефон, productId, leadId с отдельным доступом.

`RatePublished`: rateId, version, productId, audience (public/personal), customerId только для personal, условия,
validFrom, validUntil, publishedAt. Публичная и персональная ветви разделены по топикам/правам. АБС выпускает событие
лишь после согласования. Кредитный риск и портфель в событие не входят.

### 3. Транзакции, повторы и состояние

Состояния заявки: `DRAFT → OTP_PENDING → SUBMITTED → PENDING_REVIEW → APPROVED → OPENED`; при новых условиях —
`AWAITING_RECONFIRMATION → APPROVED`; возможны `REJECTED`, `EXPIRED`. Статус UI «обрабатывается» не равен `OPENED`. Срок
жизни каждого предложения фиксируется в АБС.

- Сервис в одной SQL-транзакции сохраняет заявку и outbox. Ответ «принято» выдаётся только после durable commit. Вызов
  Kafka не находится в пользовательской транзакции.
- Адаптер подтверждает offset только после commit АБС. `inbox(eventId)` и уникальный `applicationId` предотвращают
  повторную заявку. При повторе после открытия АБС возвращает ранее созданный результат, а не проводит операцию заново.
- Проверка версии/согласия, остатка, открытие/списание, привязка applicationId к счёту и запись outbox выполняются одной
  транзакцией АБС. Это обязательная доработка пакета, проверяемая spike A03.
- Доставляются как минимум один раз; используется `aggregateVersion`, обработка только ожидаемых переходов. При пропуске
  версии выполняется ограниченная сверка адаптером, не запрос из браузера в Oracle.
- Публикация outbox и подтверждение брокером не атомарны. Повторная публикация допустима: у всех потребителей есть inbox
  и уникальный eventId. Технические ошибки повторяются с backoff/jitter; неисправимые сообщения попадают в отдельную
  очередь ошибок с alert и управляемым replay.
- Отправка SMS и её receipt ведутся в отдельном журнале. Идемпотентный ключ шлюза используется при наличии; если шлюз
  его не поддерживает, после неопределённого timeout возможен дубль СМС, но не дубль финансовой операции. Для OTP повтор
  передаёт тот же действующий challenge.
- При новых условиях согласие на старую заявку не подходит. API создаёт новый challenge и публикует
  `DepositTermsAccepted`, АБС сверяет consentId и rateVersion. «Нажать кнопку ещё раз» не обходит это правило.
- Существующие прямые запросы MVC к АБС для платежей остаются отдельным legacy-путём и помечены на схеме. Новый
  депозитный сценарий не должен использовать этот путь, включая получение списка счетов (UC-07).

### 4. Нагрузка и отказоустойчивость

Каталог и состояния читаются из выделенной MS SQL, а не из Oracle. События счетов/ставок обновляют проекции
инкрементально. Начальная выгрузка и периодическая сверка — пакетно в окнах низкой нагрузки. Индексы outbox и лимиты
адаптера выбираются по нагрузочному прототипу; предварительно ограничиваем обработку, а не добавляем неограниченное
число Oracle-сессий. При перегрузке уменьшается скорость consumer, наблюдается lag и возраст заявки.

**Предлагаемая топология (A05):**

1. Экземпляры нового Java-сервиса и web/proxy работают в двух ЦОД, балансировщики проверяют health; каждый ЦОД рассчитан
   на полную согласованную нагрузку. Session state MVC выносится в его защищённую SQL-конфигурацию, ключи подписи
   общие/управляемые, локальная память не является единственным хранилищем сессии.
2. MS SQL AG: один writer, синхронная реплика между ЦОД, независимый witness, fencing старого writer. Нельзя
   одновременно писать в две расходящиеся копии. Репликация и failover нужны для новой БД и критичного состояния
   legacy-аутентификации.
3. Oracle: primary/standby Data Guard с синхронной защитой, единственный активный writer. Это отказоустойчивость, **не
   горизонтальное масштабирование АБС**. При отказе АБС новые заявки ждут, а не открываются вне неё.
4. Kafka: локальный кластер из трёх брокеров, replication factor 3, min.insync.replicas 2, acks=all; резервный кластер
   во втором ЦОД и асинхронная межкластерная репликация. При потере ЦОД могут потеряться последние копии сообщений в
   резервном Kafka. Поэтому outbox источников хранится минимум 7 дней (предложенный срок, больше DR-окна),
   подтверждённые записи защищены синхронной SQL/Oracle-репликацией. После failover — replay outbox и сверка inbox; не
   предполагается, что один только MirrorMaker обеспечивает RPO=0.
5. Внутренние балансировщики, шлюз SMS, кол-центр и его PostgreSQL должны также иметь резервирование и протестированный
   failover. Контракт доставки внешнего оператора проверяется отдельно; он влияет на доступность OTP. Без покрытия этих
   зависимостей общая цель 99,9% не достигнута.
6. При сетевом разделении приоритет у отсутствия split-brain и потери принятой заявки: неподтверждаемая синхронная
   запись отклоняется/ставится на паузу, не выдаётся ложный успех. Недоступность входит в SLO, а не скрывается из
   отчёта.

RPO=0 заявлен для сценария потери одного ЦОД при штатно синхронизированных БД, не для одновременной гибели обеих
площадок. Резервные копии и восстановление нужны отдельно. 99,9% — цель проверок и эксплуатации, не доказанное свойство
рисунка.

### 5. Приёмка и поэтапное внедрение

| Проверка                                  | Ожидаемый результат                                                                                   |
|-------------------------------------------|-------------------------------------------------------------------------------------------------------|
| UC-01…UC-07 на стенде                     | Каждый сценарий проходит по показанным компонентам и выдаёт требуемый результат                       |
| Повтор одной команды после commit Oracle  | Один счёт и одинаковый accountId в ответе                                                             |
| АБС остановлена, затем восстановлена      | Каталог/приём в пределах лимита работают; после восстановления очередь обрабатывается без перегрузки  |
| Смена ставки, чужой accountId, повтор OTP | Новое согласие / отказ в доступе / отказ повторного использования                                     |
| Потеря активного ЦОД                      | RTO/RPO проверены, outbox replay восстановил события, две БД не принимают записи одновременно         |
| СМС-шлюз недоступен                       | OTP не считается подтверждённым; уже открытый счёт не откатывается; уведомление имеет статус доставки |
| Расчётная нагрузка P-07                   | Выполняются согласованные p95, очередь не растёт бесконтрольно, Oracle не деградирует                 |

## **Альтернативы**

| Альтернатива                                        | Плюсы                         | Почему не выбрана                                                                                                                          |
|-----------------------------------------------------|-------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------|
| Доработать только MVC, читать/писать прямо в Oracle | Меньше новых приложений       | Усиливает перегрузку АБС, связывает доступность, не выполняет +I-01, зависит от ядра подрядчика                                            |
| Полностью заменить MVC и АБС микросервисами         | Единый новый стек             | Непропорциональный объём/миграционный риск для 6 месяцев; не требуется бизнесом                                                            |
| Синхронный API АБС за фасадом                       | Простая модель запроса/ответа | Фасад не устраняет зависимость и нагрузку; ручное решение всё равно асинхронно                                                             |
| Обмен XML/CSV по расписанию для всех заявок         | Доступен legacy-платформам    | Высокая задержка/сложность статусов и согласия; файлы оставлены только для партнёра в ADR-002                                              |
| Новый сервис на современном .NET                    | Хорошая преемственность MVC   | Допустимый резерв, если Java-ресурс недоступен. Для предложенного решения выбрана имеющаяся Java/Kafka-экспертиза; выбор подтвердить spike |

## **Недостатки, ограничения, риски**

| Риск                                         | Последствие                                        | Мера / владелец                                                                       |
|----------------------------------------------|----------------------------------------------------|---------------------------------------------------------------------------------------|
| Нет точки расширения MVC или доступа к шлюзу | Нельзя безопасно реализовать UC-03 без подрядчика  | Spike M1, затем минимальная согласованная доработка; интернет-банк                    |
| Ограниченный Java-ресурс                     | Срыв параллельных работ                            | Выделить команду/обучение до M2; руководитель IT                                      |
| Eventual consistency                         | Клиент кратковременно видит старую ставку/статус   | Версии, сроки действия и финальная проверка АБС; владельцы сервисов                   |
| Ручное решение MVP                           | Открытие не мгновенное, нагрузка на 50 сотрудников | Согласовать срок обработки и очередь; владелец депозитов; автоматизация M7–M12        |
| Стоимость двух ЦОД и синхронной репликации   | Дополнительные лицензии, latency, ограничения сети | Проверить A05 до обещания SLA; DBA/инфраструктура                                     |
| Legacy-платформа устарела                    | Трудная поддержка и ограничения безопасности/HA    | Изолировать новый контур; согласовать обновление ядра отдельным планом                |
| Копии данных и новые обработчики             | Дополнительные доступы и ошибки восстановления     | Роли, сроки хранения, контрактные/DR-проверки и ответственные                         |
| Остаток/условия изменились за время ожидания | Отказ или повторное подтверждение                  | Атомарная проверка в АБС; клиенту объясняется причина, без скрытого изменения условий |
